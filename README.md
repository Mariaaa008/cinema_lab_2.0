# 2 Назначение системы

Система предназначена для упрощенного бронирования билетов в кинотеатр, с целью автоматизации бронирования мест на киносеансы. 
Пользователь будет иметь доступ к расписанию сеансов, схеме залов, информации о свободных местах. После выбора пользователь может оформить бронь и получить электронный билет с QR-кодом на свою электронную почту. Система позволяет сделать отмену брони.
Администратор должен иметь возможность добавлять и изменять фильмы и сеансы.

# 3 Описание системы

## 3.1 Схема предоставления услуги

Клиент заходит на веб-сайт. Видит перед собой страницу с регистрацией или авторизацией. Если клиент выбрал регистрацию, то вводит электронную почту и пароль. Информация о новых пользователях сохраняется в базу данных. Если клиент выбрал авторизацию, он заполняет те же логин и пароль, система проверяет есть ли в базе данных эта информация при нахождении совпадений переходит на следующую страницу, если не совпадает, то выходит окно с информацией об ошибке.

Перед авторизованными пользователями страница выбора фильмов (фильмы и их описание: жанр, длительность, возрастное ограничение, постер, статус показа - хранятся в библиотеке). Далее пользователь выбирает нужный фильм и переходит на следующую страницу выбора даты и времени киносеанса. 

Схема зала хранится в базе данных. Пользователь выбирает место (или несколько мест) среди свободных (зеленые), забронированные места выделяются красным цветом. После того, как пользователь выбрал место, выходит окно с информацией о подтверждении бронирования. После подтверждения место становится недоступным для других. Пользователь получает QR-код (он создается с помощью библиотеки qrcode) на почту (система берет информацию из базы данных пользователей). Выходит сообщение «Успешно забронировано».

Клиент переходит на главную страницу (выбор фильмов), где можно перейти на страницу личного кабинета в раздел «Мои заказы», здесь хранится история заказов, а также есть возможность отмены бронирования билетов.

Данные для авторизации администратора хранятся в базе данных. Администратор авторизуется по рабочей почте и паролю. Администратор имеет доступ к каталогу фильмов и сеансов, может удалять и добавлять новые фильмы в каталог. Устанавливает время и дату сеансов, статус фильма (активный - показывают в кинотеатре, архив - просмотр информации о фильме в другом разделе).

# 5 Планы по доработке и развитию системы

В рамках дальнейшего развития проекта планируется реализовать функционал, основанный на сервисе More Cinema.

More Cinema - это существующий сервис онлайн-бронирования билетов в кинотеатр, который уже предоставляет базовый функционал, включающий каталог фильмов, расписание сеансов, регистрацию пользователей и бронирование мест. 

Проект представляет собой вторую версию системы, направленную на улучшение и расширение возможностей оригинального сервиса More Cinema. 

## 5.1 Автоматический перевод фильмов в архив
* Описание: Фильмы, у которых дата окончания проката меньше текущей даты, должны автоматически менять свой статус с «Активный» на «Архив». Это избавит администраторов More Cinema от необходимости вручную отслеживать и архивировать завершенные прокаты.
* Механизм реализации: Простая проверка на стороне Backend при загрузке страницы каталога). Если current_date > end_date, статус в БД обновляется на «Архив».

## 5.2 История показов архивных фильмов
* Описание: В разделе «Архив» пользователь сможет посмотреть, в какие даты и времена фильм фактически показывался в кинотеатре. Это расширяет функционал More Cinema, где архивные фильмы просто скрываются из каталога.
* Механизм реализации: Выборка из таблицы сеансы всех записей, связанных с конкретным фильмом, где дата сеанса уже прошла. Отображение списка дат простым текстовым списком.
  
## 5.3 Интеграция с Кинопоиском
* Описание: Для фильмов, перешедших в статус «Архив», на карточке фильма появляется кнопка «Подробнее на Кинопоиске». При нажатии пользователя перекидывает на страницу этого фильма на внешнем ресурсе.
* Механизм реализации: В модель «Фильм» в базе данных добавляется одно новое текстовое поле kinopoisk_url. Администратор при добавлении фильма просто вставляет туда ссылку. На фронтенде для архивных фильмов рендерится тег a href="{{ kinopoisk_url }}", который открывает ссылку в новой вкладке.

# 7 Тестирование и контроль работоспособности

Для понимания того, какое поведение ПО является рабочим (штатным), а какое — внештатным (ошибочным), используется анализ HTTP-кодов ответов сервера. 

## 7.1 Штатный режим работы (Успешные операции) Чтобы понять, что приложение работает корректно, сервер должен возвращать успешные коды состояния:
1. HTTP 200 OK: Страницы успешно загружаются, данные успешно получены из базы (например, открылся каталог фильмов, загрузилась схема зала, пользователь получил список бронирований).<br/>
2. HTTP 201 Created: Успешное создание новой сущности (например, пользователь успешно зарегистрировался, администратор создал новый сеанс, билет успешно забронирован).<br/>
3. HTTP 302 Found: Успешное перенаправление (например, после успешной авторизации или после оформления брони пользователя перенаправляет в личный кабинет; после выхода из аккаунта - на главную страницу).<br/>
4. HTTP 404 Not Found (Не найдено):<br/>
	Пример 1: Пользователь пытается авторизоваться, вводит электронную почту, которой нет в базе данных. Сервер возвращает 404 и сообщение «Пользователь не найден».<br/>
	Пример 2: Пользователь пытается перейти по ссылке на фильм или сеанс, который был удален администратором. Сервер возвращает 404 «Сеанс не найден».<br/>
	Пример 3: Запрос к несуществующему фильму.<br/>
6. HTTP 400 Bad Request (Некорректный запрос):<br/>
	Пример 1: Пользователь при регистрации вводит пароль короче минимальной длины или email без символа @. Сервер отклоняет запрос с кодом 400 и выводит сообщение об ошибке валидации.<br/>
	Пример 2: Пользователь пытается забронировать уже занятое место - сервер возвращает 400 с сообщением "Место уже занято".<br/>
	Пример 3: Администратор пытается создать сеанс с датой в прошлом.<br/>
7. HTTP 401 Unauthorized (Не авторизован):<br/>
	Пример 1: Пользователь ввел верный email, но неверный пароль.<br/>
	Пример 2: Пользователь пытается получить доступ к личному кабинету без повторной авторизации.<br/>
8. HTTP 403 Forbidden (Доступ запрещен):<br/>
	Пример 1: Попытка получить доступ к панели администратора без прав администратора.<br/>
	Пример 2: Пользователь пытается получить доступ к чужим данным.<br/>
9. HTTP 409 Conflict (Конфликт):<br/>
    Пример: Два пользователя одновременно пытаются забронировать одно и то же место, второй запрос получает 409

## 7.2 Внештатные ситуации и обработка ошибок 
Если что-то идет не так, система должна возвращать соответствующие коды ошибок. Примеры нештатных ситуаций:
HTTP 500 Internal Server Error (Внутренняя ошибка сервера):<br/>
	Пример 1: Произошел сбой подключения к базе данных, или в коде возникла непредвиденная ошибка.Это сигнал для разработчика о критическом сбое.<br/>
	Пример 2: Ошибка при отправке email-подтверждения брони.
# 8. Гарантийная поддержка
Исполнитель должен предоставить доступ к службе поддержки пользователей, а также доступ к персоналу, ответственному за работу с клиентами, для сообщения информации о неисправностях в системе и получения помощи по использованию системы по электронной почте.

Исправление Исполнителем ошибок в работе сервисов, а также функциональных расширений по мере их появления (время реагирования определяется степенью критичности ошибки и составляет от 1 до 5 рабочих дней дней ). Исправление ошибок осуществляется в сроки, не ниже следующих:

| Вид запроса | Максимальное допустимое время устранения инцидента, в зависимости от приоритета | | |
| :--- | :---: | :---: | :---: |
| | **Критичный** | **Высокий** | **Стандартный** |
| **Инцидент** | 1 рабочий день | 3 рабочих дня | 5 рабочих дней |

Прием запросов в техническую поддержку должен осуществляться Исполнителем круглосуточно, 24 часа в сутки, 7 дней в неделю.

Приоритет - критерий важности и срочности решения инцидента, с учетом влияния, оказываемого на пользователей ИС. В ходе эксплуатации Сервиса, должны быть выделены не менее 3-х типов приоритетов для возникающих инцидентов.

| Приоритет инцидента | Описание |
| :--- | :--- |
| 1-го приоритета (Критичный) | Аварийная внештатная ситуация, связанная с полной или частичной потерей более 50% функционала работоспособности сервиса |
| 2-го приоритета (Высокий) | Частичная потеря работоспособности ПО, не приводящая к потере критичного (основного) функционала, возможны альтернативные варианты выполнения основных функций сервиса |
| 3-го приоритета (Стандартный) | Снижение производительности, не приводящее к потере функциональности Сервиса |

Срок гарантийной поддержки: 1 год с момента выполнения обязательств по выполнению работ
(определяется датой подписания акта сдачи-приемки).
